# Инцидент: ушёл боевой токен Тинькофф

Цель: остановить торговлю и отозвать токен. Не чинить «на ходу».

Этот контур — sandbox. Боевой target включается только при `TINKOFF_LIVE=1`. Если боевой токен всё же оказался в `.env`, git, логах или чате — считать его скомпрометированным.

## Сразу

1. Kill-switch: `POST /kill` с `X-App-Token` кабины. Новые ордера не уходят.
2. На сервере в `.env`: `TINKOFF_LIVE=0`. Не ставить боевой токен обратно.
3. `systemctl restart idatagon-api idatagon-worker`.
4. В кабинете Тинькофф отозвать токен. Выпустить новый только если это снова sandbox, и только в `.env` на сервере (`chmod 600`). В git не класть.
5. Проверить открытые заявки в кабинете брокера. Лишние — снять вручную.

## Проверить, куда утекло

- `git log -p -- .env .env.example` и историю origin. В git не должно быть токена.
- Логи: `/var/www/i_datagon_ru_usr/data/logs/idatagon-api.log`, `idatagon-worker.log`, access-лог nginx. Токен заголовка кабинета туда не пишется; строку брокера всё равно поискать и вычистить ротацией.
- Бэкапы `/var/backups/idatagon`: старый дамп/копия `.env` с боевым токеном не восстанавливать как есть.
- Чаты, скриншоты, issue, CI logs.

Если токен был в публичном git — считать его известным всем. Отзыв обязателен, смена «на всякий случай» недостаточного.

## Что не делать

- Не включать `TINKOFF_LIVE=1`.
- Не коммитить `.env`.
- Не пушить «hotfix» с токеном в репозиторий.
- Не торговать с тем же токеном «пока разберёмся».
- Не писать токен в этот файл, в TZ и в кабину.

## После отзыва

Новый sandbox-токен — только в `/var/www/i_datagon_ru_usr/data/www/i.datagon.ru/.env`.  
`APP_AUTH_TOKEN` кабинета сменить, если он светился вместе с брокером.  
Запись в лог инцидента: когда заметили, где видели, время отзыва, кто рестартил юниты.
